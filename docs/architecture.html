One agent may ask. The other human sets the boundary.

How often should the receiver ask?

The recipient chooses the convenience boundary. A broader choice changes only whether another human prompt appears; it never grants another tool, workspace, model, MCP, network path, or runtime capability.

ask_always One request

Allow this turn, save no grant, and ask again for the next request.

conversation_30m One conversation · 30 minutes

Match this conversation until one fixed deadline. New activity never extends the clock.

teammate_always One authenticated teammate

Match the member identity across that teammate's current and future enrolled devices.

all_always Every teammate · this receiver

Match all authenticated members, including future members, but only on this receiving installation.

The requester cannot request, select, or inspect a standing grant. From the requester's side, every turn simply begins at awaiting_approval and progresses only when the recipient's receiver decides. The current approval surface is the CLI or authenticated loopback API—not a packaged tray UI. While a teammate runtime is active, sensitive loopback endpoints return 423 Locked; authenticated health remains available.

Who controls what?

The requester describes the work. The relay enforces shared protocol rules. The recipient owns every choice that can grant local capability.

Requester chooses

The proposal, never the teammate's machine configuration.

  • Exact teammate agent
  • Title and self-contained prompt
  • A narrower requested access level
  • Opt-in files from configured aliases
  • Expiry and idempotency key

Relay enforces

Identity, routing, state transitions, and payload bounds.

  • Bearer credential and organization membership
  • No self-loop, even across the same member's devices
  • Exact target, decision, claim, and result retries
  • Request lifecycle and expiry
  • File count, names, hashes, and byte limits

Recipient owns

The actual authority on the recipient workstation.

  • Inspect, Deny, or choose one of four approval levels
  • Claude Code, Codex, or external runner
  • Model override—or the adapter's isolated default
  • Working directory and workspace aliases
  • Writes, shell, network, MCP, and environment policy
The key invariant: a remote requester may narrow the recipient's local policy, but can never turn on a capability the recipient disabled. remote ≤ local

How files move

Files travel inline with the authenticated request as Base64-encoded bytes. Upload and download paths are constrained on the local clients; execution bytes remain behind the recipient's per-request allow_once gate.

1. Local aliasRequester selects a file beneath an explicitly configured workspace.
2. Safe readerRejects traversal, symlinks, special files, sensitive paths, and unsafe names.
3. Encodecontent_base64, byte size, MIME type, and SHA-256 travel over HTTPS.
4. InspectRecipient sees the full prompt plus file metadata—not the bytes—before deciding.
5. ExecuteOnly a per-request relay allow_once decision releases attachment bytes into the local sandbox; a standing grant may create that decision without another prompt.
6. ReturnFinished files from the exact return directory go back through the relay.
7. DownloadRequester explicitly saves beneath fixed team-relay-downloads/; no overwrite.
5 filesmaximum per request or result
2 MiBmaximum for any one decoded file
2 MiB totalmaximum decoded content in either direction
Trust boundary: the self-hosted relay administrator can read file payloads while they are retained. Base64 makes binary data transportable; it does not make it secret.

A recipient runtime must have a write-capable effective profile to produce returned files.

Retry without double-running

Network replies can be lost. The receiver records decisions, claims, and results before sending mutations. One boundary is deliberately irreversible: after local execution may have begun, a restart will not run it again.

An operating-system lock prevents two receiver daemons from sharing one local state directory. “Exactly once” cannot be guaranteed at a general agent CLI boundary; Team Relay chooses at-most-once execution after the durable start marker.

Who can see live execution progress?

The recipient daemon records bounded local progress such as starting, tool started or finished, and completion. The requester currently sees request lifecycle state and the final result through get_request_status, not a live tool transcript. Raw provider output, tool inputs, secrets, file contents, and private session IDs are deliberately not forwarded through the relay.

How administrator onboarding fits

An operator bootstraps one organization, creates short-lived single-use invitations, and privately gives one invitation to each teammate. Enrollment creates the raw device credential on the teammate's machine before contacting the relay; only its hash crosses the network. An administrator can later revoke an invite, device, or entire member.

What is real today

This architecture is implemented, not merely a diagram. It is also still a developer preview. The boundary between “proved” and “not yet” matters.

Observed and automated

Evidence from the current implementation and local verification.

  • Native relay with isolated Docker Valkey
  • Two distinct enrolled member identities
  • Real Claude Code → Codex request completed
  • Real Codex → Claude Code request completed
  • Claude follow-up resumed the private session in the original manual-approval test
  • MCP initialize, tool discovery, directory, status, and follow-up calls
  • Automated tests cover files, denial, idempotency, revocation, and recovery paths

Still a release boundary

Do not infer production readiness from the successful local flow.

  • No independent security audit
  • No application-level rate or storage quotas
  • One relay replica; SSE fan-out is process-local
  • Runtime shares the receiver daemon's OS identity and may leave a background process
  • No packaged tray notification UI or native service installer
  • No signed binary release, updater, or SBOM
  • Inline file transport only; no object storage
  • Post-start crash can require manual running-state resolution
The shortest possible mental model

Team Relay is a permissioned store-and-forward gateway. Your agent posts a proposal to shared relay state. Your teammate's receiver notices it and either asks them or matches a private grant they previously chose. The receiver still issues a fresh one-request decision, then their local runtime works under their local policy. The answer or selected deliverables travel back through the relay. Conversation stickiness preserves private runtime context without sharing the provider session ID; it does not expand permission.

Small glossary

Terms that are easy to conflate when discussing the system.

MCP
The local tool interface the requesting Claude or Codex calls. It provides connectivity, not authority over the recipient.
SSE
Server-Sent Events: one long-lived outbound HTTP response used to notify a receiver of changes.
NDJSON
Newline-delimited JSON: a stream where each line is one complete JSON object. The external runner uses it for input and events.
Conversation affinity
A Team Relay conversation ID maps to a provider session that stays private on the recipient machine.
Allow once
The relay's exact one-request decision. It is created after a prompt or a matching recipient-local grant.
Standing grant
Private, durably revocable receiver state that can skip another human prompt only within its approved resource ceiling. It never widens local runtime policy.
Idempotency
Repeating the same uncertain network mutation returns the same logical outcome instead of creating duplicate work.
